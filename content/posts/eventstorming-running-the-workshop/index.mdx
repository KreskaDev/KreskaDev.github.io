## 1. You've seen the wall. Now run the session.

The [Big Picture post](/posts/eventstorming-big-picture/) showed you what a finished
EventStorming wall looks like and how to read it. The wall doesn't appear by magic.
It comes out of a workshop — three to four hours, six to ten people in a room,
brown paper and Sharpies. The deliverable isn't a document; it's the shared mental
model now living inside everyone's head.

This post answers a different question: **what actually happens in the room?**

## 2. The format at a glance

EventStorming is **timeboxed**. Brandolini's recommendation, refined across hundreds
of public workshops, breaks one session into five distinct phases. The diagram
below is the canonical structure I run for new teams.

The thing newcomers underestimate is how much real elapsed time the first two
phases need. **Big Picture is 90 minutes of focused chaos.** You will be tempted
to compress it. Don't. The discoveries that make the workshop worth running
happen during chaotic storming, not after.

## 3. Roles in the room

A storming session is not a meeting. It's a collaborative authoring session
where six to ten people physically write the model on a wall. Each role brings
something different.

  {

    title: "Engineers",
    body: "Listen first, write second. Translate domain language into commands and aggregates. Flag invariants the domain experts assume but never state. Never say 'in the database' — the wall is pre-storage."

    title: "Product analyst",
    body: "Watches for events that connect to KPIs. Asks 'who would care if this happened?' Spots the read models the dashboard team needs months before they're requested."

## 4. What the wall looks like at the end

After three to five hours, the wall has structure. Events are timeline-ordered,
commands sit above them, aggregates are grouped, policies bridge contexts,
hot spots are marked. The diagram below is a stylized version of the **output**
of one morning of work on the lending slice of a public library.

Two bounded contexts emerged from this session: **Lending** (everything to do
with reservations, pickups, and returns) and **Billing** (member fines, which
have a different vocabulary and a different team behind them). The split itself
was a workshop discovery — it wasn't on the agenda.

A few things to notice that the diagram makes obvious but a finished document
would hide:

- **The Lending context owns the timeline.** Events flow left-to-right; commands
  arrive from actors above; aggregates squat below the events they protect.
- **The Billing context speaks a different language.** "Late fee charged" is
  an event there, not a command. The Lending side fires the policy; Billing
  reacts.
- **The hot spot is real.** A reservation triggers an email. Email service is
  external. What if it's down? The workshop noticed this; it didn't solve it.
  The red sticky is the artifact of a parked question.

## 5. Run your first workshop tomorrow

If you've never facilitated, here's the smallest checklist that survives contact
with reality.

| Item | Note |
| --- | --- |
| Wall | 8m × 1.2m of brown paper or whiteboard. Bigger than you think. |
| Sticky notes | 6 colors × 100 notes each. Buy more orange than anything. |
| Sharpies | One per person. Black, medium tip. Pencils don't work. |
| Timer | Visible to the whole room. Phone is fine. |
| Facilitator | Not the most senior engineer — that's the dominant-voice problem. Someone who can say "park it" without flinching. |
| First slice | Pick one end-to-end flow. "Member reserves book and picks it up" is good. "All of acquisitions" is not. |
| Pre-read | None. Walking in cold is the point. |

## 6. What can go wrong inside the room

  {
    variant: "negative",
    title: "Note-takers instead of writers",
    body: "Someone hangs back and watches. They aren't writing stickies. Every silent person is a missing perspective. Hand them a Sharpie. Don't proceed until they're at the wall."
  },
  {
    variant: "negative",
    title: "The loud architect",
    body: "One engineer explains the system to the room. Domain experts go quiet. Stickies stop appearing because everyone is listening to one voice. Facilitator must intervene: 'Quiet for two minutes. Everyone writes.'"
  },
  {
    variant: "negative",
    title: "Jumping to code mid-storm",
    body: "Someone says 'OK so we'd have a Reservation table with a foreign key to...'. Stop. Storage decisions belong nowhere on this wall. The wall is pre-storage. Pre-API. Pre-anything."
  },
  {
    variant: "negative",
    title: "Compressing chaotic storming",
    body: "The room runs out of orange events after 20 minutes and the facilitator says 'OK let's move on.' Don't. The next 70 minutes are where edge cases surface. Sit with the silence; new stickies will appear."
  }
]} />

## 7. Tooling — physical first, remote second

I default to a physical wall. Reasons: tactile writing is faster than typing,
peripheral vision shows the whole timeline, and the room reads each other's
body language. Miro and Mural work — I've run remote stormings — but the
facilitation discipline must be harder, breaks must be more frequent, and the
output diverges measurably for first-time teams.

If you have to run it remote: shorter sessions (60 minutes max), more of them,
and one person dedicated to keeping the canvas tidy in real time. Otherwise
you finish with a Mural board no one revisits.
